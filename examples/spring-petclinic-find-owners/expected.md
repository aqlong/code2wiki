## Summary

A user searches the clinic's owner records by last name. If exactly one owner matches, the system takes them straight to that owner's profile page. If many owners match, a paginated list is shown. If no owners match, the search form is shown again with a "not found" message.

## Actor and triggers

- **Actor:** Visitor or unauthenticated user (no access restrictions are enforced on this endpoint).
- **Trigger:** The user submits the owner search form, or follows a `/owners?lastName=...` link.

## Preconditions

- The user has navigated to the owner search form.

## Main flow

1. The user enters a last name (or leaves it blank) and submits the search.
2. The system reads the last name. If it is blank, it is treated as "match anything," returning every owner.
3. The system retrieves owners whose last name starts with the search term, one page at a time (5 owners per page).
4. The system decides what to show based on how many owners matched.

## Alternate and exception flows

- **No owners match:** The search form is re-shown with the error "not found" attached to the last-name field. No redirect.
- **Exactly one owner matches:** The user is silently redirected to that owner's profile page (`/owners/{id}`). They never see the list view.
- **More than one owner matches:** A paginated list is shown with the current page number, total page count, and total result count.
- **Page parameter omitted or out of range:** Defaults to page 1. (Out-of-range pages produce an empty result page from the database, which currently renders as the same "no results" branch.)

## Postconditions

- On success: the user is on the search results list, an owner profile, or back on the search form with an error.
- No data is modified by this use case.

## Business rules

- **Empty search returns everything.** A blank last name is silently treated as "match all" (uses an empty-string prefix). This is intentional: the form is also reachable via `GET /owners` with no parameters.
- **One match is a hidden redirect.** When exactly one owner matches the search, the user is taken straight to that profile page — they do not see a one-row list. A non-developer reader needs to know this because it changes the URL pattern unexpectedly.
- **Search is a prefix match on last name only.** First name and other fields are ignored.
- **Page size is 5 owners per page.** Hard-coded; not configurable from the search form.

## Suggested test scenarios

- **Happy path with multiple matches** — Given the clinic has owners "Smith", "Smithson", and "Smithers", when a visitor searches for "Smith", then a paginated list is shown with 3 results on page 1 of 1.
- **Single match redirects** — Given the clinic has exactly one owner named "Wilson", when a visitor searches for "Wilson", then the visitor is redirected to that owner's profile and never sees the list view.
- **No matches show error** — Given no owners have a last name starting with "Xylo", when a visitor searches for "Xylo", then the search form is shown again with a "not found" error on the last-name field.
- **Empty search returns all owners** — Given the clinic has 23 owners, when a visitor opens `/owners` with no last-name filter, then a paginated list is shown with 5 owners on page 1 of 5.
- **Pagination via `page` parameter** — Given a search returns 12 results and the visitor requests `page=2`, then results 6–10 are shown with pagination metadata indicating page 2 of 3.
- **Prefix match, not contains** — Given the clinic has an owner "Smith" and an owner "Goldsmith", when a visitor searches for "smith", then only "Smith" is returned (the prefix match excludes "Goldsmith").
