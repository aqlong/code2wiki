## Summary

A signed-in author permanently deletes one of their own posts. The system shows a confirmation page first, then removes the post from the database on confirmation and redirects to the post list with a success message.

## Actor and triggers

- **Actor:** Signed-in author who owns the post.
- **Trigger:** The author submits the delete confirmation form (`POST /blog/posts/{pk}/delete/`).

## Preconditions

- The author is authenticated.
- The post identified by `pk` exists and belongs to the signed-in author.

## Main flow

1. The author navigates to the delete URL (`GET /blog/posts/{pk}/delete/`).
2. The system shows a confirmation page naming the post.
3. The author confirms by submitting the form (POST).
4. The system verifies the author still owns the post.[^queryset]
5. The system permanently deletes the post row from the database.
6. The system shows a success message ("Post deleted.") and redirects to the post list.

[^queryset]: `get_queryset()` scopes the lookup to `Post.objects.filter(author=self.request.user)`, so a deletion attempt on another user's post returns 404.

## Alternate and exception flows

- **Wrong author / not found:** The system returns 404 on both GET and POST. The author cannot determine whether the post belongs to someone else.
- **Unauthenticated:** Redirected to the login page.

## Postconditions

- The post row no longer exists in the database.
- The author is on the post-list page with a one-time "Post deleted." message visible.
- Any related objects with a `CASCADE` or `SET_NULL` foreign key to the post are affected according to their model definition.

## Business rules

- **Only the author can delete their own posts.** The queryset scope prevents deleting another user's content.
- **Deletion is permanent and immediate.** There is no soft-delete or recycle bin. A deleted post cannot be recovered through the application.
- **A confirmation step is required.** A GET to the delete URL shows a confirmation page; no data is modified until the author POSTs.

## Suggested test scenarios

- **Happy path** -- Given a signed-in author with their own post, when they confirm deletion, then the post is removed from the database and they are redirected to the post list with a success message.
- **Wrong author** -- Given user B's post, when user A submits the delete form, then the system returns 404 and the post still exists.
- **GET shows confirmation** -- Given a signed-in author, when they GET the delete URL, then a confirmation page is shown and no data is modified.
- **Unauthenticated** -- Given a signed-out user, when they GET the delete URL, then the system redirects to login.
- **Already deleted** -- Given a post that has already been deleted, when the author follows a stale delete link, then the system returns 404.
